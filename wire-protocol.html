MySQL and MariaDB Wire Protocol Reference

This is an LLM-generated compilation of the Oracle MySQL protocol documentation and the MariaDB client/server protocol documentation, checked against both server sources and raw packets from running servers. Replication (COM_BINLOG_DUMP, COM_REGISTER_SLAVE and binlog events), the X Protocol, and COM_CLONE are out of scope.

Protocol Basics

  • Transport: TCP (default port 3306), Unix domain socket, and on Windows named pipes or shared memory. The client connects; the server sends the first packet.
  • Byte order: little-endian for integers.
  • State: stateful and strictly request/response, except for progress packets and COM_STMT_SEND_LONG_DATA/COM_STMT_CLOSE, which get no response.
  • Phases: connection phase, then command phase until either side closes. A replication command moves the connection into binlog streaming.

Identifying the Server

Read both signals from the greeting:

  1. If capability bit 0 is clear, the server is MariaDB, and the 4 bytes at offset 6 of the reserved block are extended capabilities.
  2. If the version string contains mariadb (case-insensitive), the server is MariaDB. Versioned features such as COM_RESET_CONNECTION have no capability flag, so they depend on this and the version number.
ServerBit 0Version string
MySQLSetFor example 8.4.8
MariaDB 11.0 and laterClearFor example 11.4.12-MariaDB; no prefix by default
MariaDB 10.xClear on current releases; older releases set itDefault prefix 5.5.5-, for example 5.5.5-10.11.6-MariaDB

Extended capabilities are valid only when bit 0 is clear. When bit 0 is set, treat those 4 bytes as reserved.

To negotiate extended capabilities, the client must also clear bit 0 in its own capabilities and put its extended capabilities at the same position in the response.

MariaDB reads the client's extended capabilities only when bit 0 of the client flags is clear (parse_client_handshake_packet).

Packet Framing

COM_QUIT as a complete packet is 01 00 00 00 01: length 1, sequence 0, command 01.

Sequence ID

  • The client's command packet has sequence 0, and each later packet in that exchange increments it, wrapping from 255 to 0.
  • Sequence resets to 0 for each new command. In the connection phase the greeting has sequence 0, and the sequence continues across the whole authentication exchange.
  • A reply inside a multi-step exchange uses the last received sequence plus 1.
  • Responses to pipelined commands each restart at sequence 1, so sequence alone cannot match a reply to a command.

Payloads of 2^24-1 Bytes or More

  • A logical payload of 16 777 215 bytes (FF FF FF) or more is split into consecutive packets, each with an incremented sequence.
  • A packet with length FF FF FF means another packet continues the payload. The payload ends at the first packet shorter than that.
  • If the total is an exact multiple of 2^24-1, an empty packet (00 00 00, next sequence) terminates it.
  • A logical payload larger than the server's max_allowed_packet makes the server report an error and close the connection.
40 MB payload:
ff ff ff 00 <16 777 215 bytes>
ff ff ff 01 <16 777 215 bytes>
02 00 80 02 <remaining bytes>

Payload of exactly 16 777 215 bytes:
ff ff ff 00 <16 777 215 bytes>
00 00 00 01

Compression

Compression is a separate layer under the packet framing. It starts after the OK packet that ends the connection phase, so the OK itself is uncompressed. TLS encrypts the compressed bytes.

MySQL
Enabled by CLIENT_COMPRESS (zlib) or CLIENT_ZSTD_COMPRESSION_ALGORITHM (zstd). If both are negotiated, zlib is used. With zstd, the response also carries zstd_compression_level. The server variable protocol_compression_algorithms controls what it offers.
MariaDB
Enabled by CLIENT_COMPRESS (zlib). Zstandard is not supported.

TLS

TLS is offered through CLIENT_SSL in the greeting. There is no way to start TLS before the greeting.

  1. The server sends the greeting in cleartext.
  2. The client sends SSLRequest with sequence 1 and CLIENT_SSL set.
  3. The client starts the TLS handshake on the same socket. No plaintext reply comes from the server.
  4. The client sends HandshakeResponse41 inside TLS with sequence 2, and repeats its capabilities.

MariaDB zero-configuration TLS

MariaDB From 11.4, a server without configured certificates generates a temporary self-signed one, and a client can verify it without a CA:

  1. The client tolerates a certificate validation failure during the TLS handshake, records the SHA-256 fingerprint of the certificate, and continues.
  2. During an untrusted session it uses only mysql_native_password, client_ed25519 or parsec with a non-empty password, so the password is not exposed.
  3. The server's connection-ending OK has an info holding a verification digest.
  4. The client computes SHA-256 over password_hash + scramble + fingerprint and closes the connection if it does not match.

mysql_native_password

token = SHA1(password) XOR SHA1(scramble + SHA1(SHA1(password)))

An empty password sends an empty token (length 0), not 20 zero bytes. There is one challenge and one response, then OK or ERR.

caching_sha2_password

token = SHA256(password) XOR SHA256(SHA256(SHA256(password)) + scramble)

An empty password sends an empty token. The server replies OK or ERR with no more exchange.

ciphertext = RSA_OAEP(server_public_key, (password + 00) XOR scramble)
             scramble repeats cyclically to the length of password + 00; 20 bytes, no trailing 00
             OAEP padding uses SHA-1
On MySQL 8.4.8: TCP first login returned 01 04 (sequence 2). Sending 02 (sequence 3) returned 01 2d 2d 2d 2d 2d 42 45 47 ... (sequence 4). After a cleartext login on the Unix socket filled the cache, a TCP login returned 01 03 (sequence 2) and OK (sequence 3).

The cache is cleared by a server restart, FLUSH PRIVILEGES and password changes, so a client must handle 01 04 on every connection.

sha256_password

  • On TLS, the client sends password + 00 in cleartext.
  • Otherwise the client sends 01 to request the public key (not 02 as in caching_sha2_password), the server replies 01 + PEM, and the client sends the RSA ciphertext.
  • A client with the key already can send the ciphertext directly.

mysql_clear_password

The client sends password + 00 with no transformation. Use it only over a secure transport. The server still sends a 20-byte scramble, which the client ignores.

client_ed25519

MariaDB The server sends a random nonce; the client replies with the Ed25519 signature of it, keyed from the password.

parsec

  1. The server sends a 32-byte nonce as plugin_data.
  2. The client sends an empty packet to request ext-salt.
  3. The server replies with ext-salt: string<1> P (PBKDF2), int<1> iteration factor (iterations = 1024 << factor), string<EOF> salt.
  4. The client derives a key with PBKDF2-SHA512, and generates a 32-byte client nonce.
  5. The client signs server_nonce + client_nonce with Ed25519 using the derived key as the private key.
  6. The client replies with string<32> client nonce and string<64> signature.

dialog

Statement ID -1 and Pipelining

MariaDB Statement ID 0xFFFFFFFF in COM_STMT_EXECUTE, COM_STMT_BULK_EXECUTE and related commands means the last statement prepared on this connection. If the prepare failed, the execute fails too. A connector can send prepare and execute without waiting, saving a round trip on the first execution.

MariaDB answered the pipelined pair with a prepare response and a result set. MySQL answered with a prepare response and ERR 1243, Unknown prepared statement handler (4294967295). MariaDB documents this as tied to MARIADB_CLIENT_STMT_BULK_OPERATIONS, though the capture worked without negotiating it.

Pipelining

Neither vendor defines a general pipelining mode. A client can write several commands before reading, and a server reads and answers them in order, as in the capture above. Keep these limits in mind:

  • Replies must be read in order and matched by position, since sequence restarts for each one.
  • An error does not stop later commands. In the capture on both servers, a syntax error followed by COM_PING got ERR and then OK.
  • A client must keep reading while writing, or a large response can deadlock both sides on full socket buffers.

Connection Redirection

MariaDB From 11.3, setting the system variable redirect_url delivers a new server address through session tracking, because the variable is in the default session_track_system_variables.

mariadb://[user[:password]@]host[:port]/[db[?option=value[&option=value]]]
mysql:// is also accepted. The ttl option is the time in ms to remember the redirect; 0 disables caching.
  • A client can apply it when it arrives in the connection-ending OK, by connecting to the target right away.
  • A client that follows it later must wait until SERVER_STATUS_IN_TRANS is clear, then reconnect.

Implementation Checklist

  1. Framing: reassemble split packets before parsing, including the empty trailing packet. Do the same when sending.
  2. Classification: use the table, not the first byte alone. Do not test for a length under 9 under CLIENT_DEPRECATE_EOF.
  3. Non-OK replies: COM_STATISTICS returns raw text. COM_SET_OPTION and COM_DEBUG start with FE. COM_STMT_CLOSE and COM_STMT_SEND_LONG_DATA return nothing.
  4. Empty passwords: send a zero-length auth response. Do not hash an empty password.
  5. Auth switch data: strip the trailing 00 before using a 20-byte scramble.
  6. Greeting: parse the 4 reserved bytes as extended capabilities only when bit 0 is clear.
  7. Bitmaps: rows have offset 2; parameters have offset 0.
  8. TLS: fail when a required CLIENT_SSL is absent, because the greeting is unauthenticated.
  9. Cursors: expect a terminator after definitions under CLIENT_DEPRECATE_EOF when CURSOR_EXISTS is set.
  10. Metadata: use the definitions of each result. Prepare-time types can differ from execute-time types.
  11. MySQL query attributes: if negotiated, every COM_QUERY needs the prefix.
  12. MariaDB progress: if negotiated, treat ERR with code 0xFFFF as a non-terminal packet.
  13. Collations: use SET NAMES, since the one-byte handshake field cannot hold every ID.
